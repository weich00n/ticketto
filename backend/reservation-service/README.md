# reservation-service

Holds, releases and confirms tickets. Redis carries the live state (availability counters,
hold liveness, expiry); MySQL carries the durable record. Listens on **8081**.

Tickets are sold by category and quantity ("2 tickets in CAT1"), never by seat. A buyer may hold
or buy at most 5 tickets per event. A hold lasts 5 minutes for the buyer, plus 1 minute for a
payment that lands on the deadline. `PLAN.md` explains the design and how each part was built.

## What it serves

| Route | Caller |
| --- | --- |
| `GET /api/v1/events/{event_id}/availability` | anyone, through API Gateway |
| `POST /api/v1/reservations` | buyer: create a hold with Queue's admission token (`Idempotency-Key` supported) |
| `GET` / `DELETE /api/v1/reservations/{hold_id}` | buyer: read or release their own hold |
| `GET /internal/v1/reservations/{hold_id}` | Checkout: price snapshot and state |
| `POST /internal/v1/reservations/{hold_id}/confirm` | Checkout: after a verified payment |
| `GET /internal/v1/events/{event_id}/capacity` | Queue: sizing admission batches |
| `GET /internal/v1/admissions/{admission_id}/reservation` | Queue: before releasing a slot |
| `POST /internal/v1/events/{event_id}/inventory` / `.../cancellation` | tests and broker-less runs; the same as `EventPublished` / `EventCancelled` |
| `GET /health` | load balancer |

The buyer is whoever API Gateway put in `X-User-Sub`; this service verifies no access tokens.
`/internal/v1/*` is not routed through the gateway.

Messages, through rabbitmq-service's broker (this service declares no queue or exchange):

- **Consumes** `EventPublished` (seeds inventory and prices) and `EventCancelled` (releases unpaid
  holds, owes refunds for paid ones).
- **Publishes** to `reservation.events`, through a transactional outbox: `ReservationExpired`
  and `RefundRequired` for Checkout, `EventSoldOut` for Queue.

## Running it

Docker is the only thing you need installed — Maven and the JDK come from the build image, so
there is nothing to set up and no version to match.

```bash
# 1. Queue signs admission tokens; a laptop stands in for it with a throwaway keypair.
eval "$(scripts/dev-admission-keypair.sh)"

# 2. Build the jar and start the service with Redis and MySQL behind it.
docker compose --profile app up -d --build

curl localhost:8081/health
```

The service refuses to start without Queue's public key, which is what step 1 exports. Drop
the `--profile app` to start only Redis and MySQL.

```bash
docker compose logs -f reservation-service   # follow it
docker compose --profile app down             # stop everything
```

## Running the tests

```bash
docker compose --profile test run --rm test
```

Maven runs inside a container against the Redis, MySQL and RabbitMQ that Compose starts first, so this
works on a machine with no Maven and no JDK. It mounts the working tree, so it tests your
uncommitted changes; `target/` and the dependency cache live in named volumes, which keeps the
build from writing into your checkout and keeps the downloads for the next run.

To pass Maven anything else, override the command:

```bash
docker compose --profile test run --rm test mvn -B test -Dtest=AdmissionEnforcementTest
```

### Lint

CI's `lint` job runs Checkstyle and SpotBugs, which needs no Redis, MySQL or RabbitMQ:

```bash
./mvnw -B compile checkstyle:check spotbugs:check
```

Checkstyle (`config/checkstyle.xml`) looks for unused and likely-wrong code, such as unused
imports, empty catch blocks and `equals` without `hashCode`, and leaves layout alone. SpotBugs
looks for bug patterns; `config/spotbugs-exclude.xml` lists the findings it ignores and why.

### Contract tests

`src/contract-test/java/.../TickettoContractTest` checks this service against the AMQP message
contracts owned by rabbitmq-service. The tests are generated by rabbitmq-service's Java
`ticketto-contracts` package, from its catalogue:

- **Publishing** (`ReservationExpired`, `RefundRequired`, `EventSoldOut`): the real `OutboxWriter`
  records each message and the real `OutboxPublisher` sends it, through the `RabbitTemplate` Spring
  Boot builds from `application.properties`, onto a recording connection instead of a broker. It
  checks the exchange, routing key, `mandatory`, publisher confirms, the AMQP properties, the
  envelope, and the payload against its schema. The recording connection acks each publisher
  confirm, as the broker would.
- **Consuming** (`EventPublished`, `EventCancelled`): the `@RabbitListener` queues are exactly
  ours, and `EventMessageListener` acks a body with only the fields Event Service always sends,
  ignores fields it doesn't know, and dead-letters a body missing a required field. The outcome
  follows `application.properties` (`default-requeue-rejected=false`).

Only the messaging beans run, with RabbitMQ's, Jackson's and validation's auto-configuration under
the test profile; MySQL and Redis are mocked, so nothing has to be running:

```bash
./mvnw -Pcontract-tests test -Dtest=TickettoContractTest -Dsurefire.failIfNoSpecifiedTests=false
```

The package comes from rabbitmq-service's GitLab package registry, and only the `contract-tests`
profile adds it (with `src/contract-test/java`), so the image build and the other jobs never need
that registry. The version is `contracts.version` in `pom.xml`; to move to a new contract version,
change it (rabbitmq-service's `contracts/CHANGELOG.md` says what changed). If the registry is
private, give Maven a token for the `ticketto-contracts` server in `~/.m2/settings.xml`.

In CI, `contract-tests` runs them on every pipeline. rabbitmq-service also triggers a pipeline here
(on `main`) for every contract merge request that affects reservation-service, with
`CONTRACTS_VERSION` set to that merge request's pre-release. Those pipelines run only
`contract-tests`, never build or deploy. A failure blocks a patch or minor contract change, and is
a warning for a major one.

#### GitLab settings the contract trigger needs

Without these, a contract merge request that affects this service fails to trigger its tests:

- here: Settings → CI/CD → Variables → "Minimum role to use pipeline variables" set to
  Developer, since the trigger passes `CONTRACTS_VERSION` as a pipeline variable
- here: anyone whose contract merge requests should trigger it needs at least the Developer role
- in rabbitmq-service: Settings → CI/CD → Job token permissions lists this project, if its
  package registry is private

## Building without Docker

`mvn` is probably not on your PATH, and the project does not expect it to be — use the Maven
wrapper, which downloads the pinned Maven 3.9.16 on first use. This path needs a local JDK 21+
and `docker compose up -d` for Redis and MySQL. `BrokerIntegrationTest` also needs a RabbitMQ on
`localhost:5672` (management API on `15672`): start rabbitmq-service's local broker with its
`docker compose up -d --build`. The test loads the topology itself, so a plain
`rabbitmq:4.3.6-management` with the `ticketto` / `ticketto-local` login works too.

```bash
docker compose up -d        # Redis + MySQL only
./mvnw clean test
./mvnw spring-boot:run      # after the eval step above
```

On Windows use `mvnw.cmd` in place of `./mvnw`.

## Configuration

Everything is an environment variable with a working default, so the table below is only what
you would change locally. See `src/main/resources/application.properties` for the rest.

| Variable | Default | Meaning |
| --- | --- | --- |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | `localhost` / `6379` / none | Redis |
| `DB_HOST` / `DB_PORT` / `DB_NAME` | `localhost` / `3306` / `reservation_db` | MySQL |
| `DB_USERNAME` / `DB_PASSWORD` | `root` / `root` | MySQL login |
| `RABBITMQ_URL` | `amqp://localhost:5672/%2F` | The broker. Without credentials in the URL, `RABBITMQ_USERNAME` / `RABBITMQ_PASSWORD` (`ticketto` / `ticketto-local`) |
| `ADMISSION_TOKEN_ALGORITHM` | `RS256` | `RS256` in deployment; `HS256` only for tests |
| `ADMISSION_TOKEN_PUBLIC_KEY` | — | Queue's public key, PEM. Required for `RS256` |
| `ADMISSION_TOKEN_SECRET` | — | The shared secret. Required for `HS256` |
| `HOLD_TTL_MINUTES` | `6` | Redis hold lifetime |
| `PAYMENT_DEADLINE_MINUTES` | `5` | What the buyer sees as `payment_expires_at` |
| `MAX_TICKETS_PER_USER` | `5` | Per-user cap |
| `EXPIRY_SWEEP_SECONDS` / `RECONCILE_SECONDS` / `OUTBOX_PUBLISH_SECONDS` | `10` / `60` / `1` | How often the expiry sweep, the MySQL reconciliation and the outbox publisher run |

## Deploying

Every push to `main` is tested, built, pushed to ECR and rolled out to ECS Fargate by the GitLab
pipeline. The AWS side is an OpenTofu stack in `deploy/terraform`. `deploy/README.md` covers
both: first deployment, secrets, CI variables, migrations, autoscaling and troubleshooting.
