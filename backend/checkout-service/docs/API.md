# Checkout Service API Endpoints

Checkout Service turns a buyer's reservation hold into a paid order. It prices the order from the hold, takes the payment through Stripe (PaymentIntents and the Payment Element), confirms the hold with Reservation Service once Stripe reports the payment, and refunds orders when an event is cancelled or a refund is owed.

It does not manage events, availability, holds or tickets. It reads and confirms holds through Reservation Service's internal API, learns about cancellations, expiries and owed refunds through RabbitMQ, and never reads another service's database.

## Conventions

| Item | Rule |
| --- | --- |
| Base URL | `https://x0vxfeenrl.execute-api.us-east-1.amazonaws.com` (the team's shared API Gateway) |
| Base path | Public routes: `/api/v1`. Stripe webhook: `/webhooks/stripe`. Health: `/health`, `/ready` (VPC only) |
| Format | JSON over HTTPS |
| Field names | snake_case |
| Identifiers | UUID strings (`order_id`, `payment` and `refund_id` are generated by checkout; `hold_id`, `event_id`, `category_id` come from Reservation Service) |
| Money | Integer minor units with a currency: `10000` + `"SGD"` is S$100.00. Amounts always come from the hold, never from the client |
| Time | UTC, ISO 8601, e.g. `2026-11-20T12:00:00Z` |
| Pagination | `page` (default 1, 1–10000) and `page_size` (default 20, 1–100). Values outside the range are clamped, not rejected; a non-integer is `400`. Lists return `items`, `total`, `page` and `page_size` |
| Correlation | Clients may send `X-Correlation-Id`. The service returns it in the response header and in error bodies, forwards it to Reservation Service and logs it. If absent or malformed, the service generates one |

### Authentication

The order routes sit behind API Gateway's Cognito JWT authorizer. Send the Cognito **access** token (not the ID token):

```
Authorization: Bearer <access token>
```

The gateway validates the token, then sets these headers and overwrites any the caller sent, so a buyer can't act as someone else:

| Header | Meaning |
| --- | --- |
| `X-User-Sub` | The buyer's `user_id` (the token's `sub`). Must equal the hold's `user_id` |
| `X-User-Username` | The token's `username` (only access tokens carry it) |

Without a valid token the gateway answers `401 {"message": "Unauthorized"}` and checkout never sees the request. Checkout's own `401 UNAUTHENTICATED` only happens if a request reaches it without `X-User-Sub`, which security groups prevent from outside the VPC.

Buyers can see only their own orders and holds. Another buyer's order or hold returns `404`, not `403`, so the response does not reveal that it exists.

The Stripe webhook has no authorizer; its only authentication is the `Stripe-Signature` header.

### Errors

Every error from checkout uses `{"error": {"code": "<CODE>", "message": "<text>"}, "correlation_id": "<uuid>"}`.

| HTTP | Code | When |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Missing or non-JSON body, missing `hold_id`, invalid `delivery_email`, or a non-integer `page` / `page_size` |
| 401 | `UNAUTHENTICATED` | `X-User-Sub` missing (see Authentication) |
| 404 | `HOLD_NOT_FOUND` | The hold does not exist or belongs to another buyer |
| 404 | `ORDER_NOT_FOUND` | The order does not exist or belongs to another buyer |
| 409 | `HOLD_EXPIRED` | The hold has expired; the buyer must select tickets again |
| 409 | `EVENT_CANCELLED` | The hold's event has been cancelled |
| 409 | `ORDER_STATE_CONFLICT` | The hold can no longer be purchased (any other non-active state) |
| 409 | `IDEMPOTENCY_KEY_CONFLICT` | The `Idempotency-Key` was used before with a different `hold_id` or `delivery_email` |
| 500 | `INTERNAL_ERROR` | Unexpected error; logged with the correlation ID. Also returned while the database is unavailable |
| 503 | `RESERVATION_UNAVAILABLE` | Reservation Service could not be reached; retry |
| 503 | `STRIPE_UNAVAILABLE` | Stripe could not create the payment; the order is saved, so retrying the same request completes it |

Webhook-only codes are listed under endpoint 4.

## Statuses

Checkout keeps three separate state machines: the order (booking), its payment and its refunds.

### Order `status`

| Status | Meaning |
| --- | --- |
| `PENDING_PAYMENT` | Created; waiting for the buyer to pay with the `client_secret` |
| `CONFIRMING` | Stripe reported the payment; checkout is confirming the hold with Reservation Service (retried automatically if Reservation is briefly unavailable) |
| `CONFIRMED` | The hold is confirmed; tickets are issued from `OrderConfirmed`. Final unless a refund is later owed |
| `EXPIRED` | The payment deadline passed before a payment arrived; the payment is cancelled. Final |
| `CANCELLED` | The event was cancelled, or a refund became owed; any payment is refunded. Final |
| `RECONCILIATION` | Reservation reported a conflict (for example, the hold belongs to another order). Needs a person; never resolved automatically |

Allowed transitions: `PENDING_PAYMENT → CONFIRMING | EXPIRED | CANCELLED`; `CONFIRMING → CONFIRMED | PENDING_PAYMENT | EXPIRED | CANCELLED | RECONCILIATION`; `CONFIRMED → CANCELLED`.

### `payment.status`

`PENDING` (waiting), `SUCCEEDED` (final), `FAILED` (declined; the buyer can retry on the same payment until the deadline), `CANCELLED` (closed at the deadline). Stripe's report of a success is always recorded, even after `FAILED` or `CANCELLED`; the order then decides whether that money confirms the booking or is refunded.

### Refund `status`

`REQUESTED` (owed, not yet sent to Stripe), `PENDING` (Stripe is processing), `SUCCEEDED` (final), `FAILED` (Stripe refused; needs a person), `REQUIRES_ACTION` (Stripe needs manual action). Refund `reason` is one of `event_cancelled`, `expired_payment`, `refund_required`, `confirm_rejected`, `late_payment`. An order is refunded at most once.

## Order object

```json
{
  "order_id": "e1f2a3b4-c5d6-4e7f-8a9b-0c1d2e3f4a5b",
  "status": "PENDING_PAYMENT",
  "hold_id": "9a8b7c6d-5e4f-4a3b-2c1d-0e9f8a7b6c5d",
  "event_id": "c4a1e8f2-91d0-4b6a-a3e5-7e2b5d8f6c90",
  "category_id": "b05e8625-6d43-4252-ad2c-bda3222a769b",
  "quantity": 2,
  "unit_amount": 5000,
  "total_amount": 10000,
  "currency": "SGD",
  "delivery_email": "buyer@example.com",
  "payment": {
    "status": "PENDING",
    "amount": 10000,
    "currency": "SGD",
    "succeeded_at": null,
    "failed_at": null
  },
  "refunds": [],
  "client_secret": "pi_3Q..._secret_...",
  "created_at": "2026-11-20T12:01:00Z",
  "updated_at": "2026-11-20T12:01:00Z"
}
```

`client_secret` is the Stripe PaymentIntent client secret for the Payment Element. It is returned only by `POST /api/v1/orders`, and only while the order is `PENDING_PAYMENT` with a payment of `PENDING` or `FAILED`; otherwise it is `null`. It is `""` (empty) when the order already exists but Stripe is briefly unreachable: retry the `POST`. `GET` responses always return `null`.

Each entry in `refunds` is `{"refund_id", "amount", "currency", "reason", "status", "stripe_refund_id", "last_error"}`; `stripe_refund_id` and `last_error` may be `null`.

## Checkout Service API endpoints

Checkout exposes 6 HTTP endpoints: 3 for buyers, 1 Stripe webhook and 2 health checks. The gateway routes only the first four.

## Buyer endpoints

All routes in this section need `Authorization: Bearer <Cognito access token>`.

### 1. Create an order

| Field | Value |
| --- | --- |
| Endpoint | `POST /api/v1/orders` |
| Parameters | Header: `Authorization` (required). Header: `Idempotency-Key` (optional, any string; recommended) |
| Request body | `{"hold_id": "<uuid>", "delivery_email": "buyer@example.com"}`. `customer_email` is accepted instead of `delivery_email`. Any other field (including quantity or price) is ignored |
| Response type | application/json |
| 201 Created | A new order in `PENDING_PAYMENT` with its `client_secret` (order object) |
| 200 OK | The order for this hold already exists (or the same `Idempotency-Key` + body was sent before): returns that order. While it is still unpaid, `client_secret` is included again, so a reload or retry can continue paying |
| 400 Bad Request | `VALIDATION_ERROR`: no JSON body, missing `hold_id`, or `delivery_email` not a valid address (max 320 characters) |
| 404 Not Found | `HOLD_NOT_FOUND`: no such hold, or it belongs to another buyer |
| 409 Conflict | `HOLD_EXPIRED`, `EVENT_CANCELLED`, `ORDER_STATE_CONFLICT` (hold not purchasable), or `IDEMPOTENCY_KEY_CONFLICT` |
| 503 Service Unavailable | `RESERVATION_UNAVAILABLE` (hold could not be read) or `STRIPE_UNAVAILABLE` (payment could not be started; the order is saved and a retry completes it) |

One order per hold: repeating the request for the same hold always returns the same order, whatever the `Idempotency-Key`. Ownership is checked before the hold's status, so a foreign hold is always `404`.

### 2. List my orders

| Field | Value |
| --- | --- |
| Endpoint | `GET /api/v1/orders?page=1&page_size=20` |
| Parameters | Header: `Authorization` (required). Query: `page` (optional, default 1), `page_size` (optional, default 20, max 100) |
| Request body | None |
| Response type | application/json |
| 200 OK | The caller's orders in every status, newest first (`created_at` descending); an empty list if there are none. `{"items": [{ "...": "order object" }], "total": 3, "page": 1, "page_size": 20}`. `client_secret` is `null` in list items |
| 400 Bad Request | `VALIDATION_ERROR`: `page` or `page_size` is not an integer |

### 3. Get an order

| Field | Value |
| --- | --- |
| Endpoint | `GET /api/v1/orders/{order_id}` |
| Parameters | Path: `order_id` (required). Header: `Authorization` (required) |
| Request body | None |
| Response type | application/json |
| 200 OK | The order object (`client_secret` is `null`). Poll this after paying: `status` moves from `PENDING_PAYMENT` to `CONFIRMING` when Stripe's webhook arrives, then to `CONFIRMED` once Reservation confirms the hold (retried every ~10 s if Reservation is unavailable) |
| 404 Not Found | `ORDER_NOT_FOUND`: no such order, or it belongs to another buyer |

## Stripe webhook

### 4. Receive a Stripe event

| Field | Value |
| --- | --- |
| Endpoint | `POST /webhooks/stripe` |
| Caller | Stripe only. Registered in the Stripe dashboard (test mode) for `payment_intent.succeeded`, `payment_intent.payment_failed` and `charge.refunded` |
| Parameters | Header: `Stripe-Signature` (required) |
| Request body | The raw Stripe event, unchanged; the signature is verified against these exact bytes |
| Response type | application/json |
| 200 OK | `{"status": "<outcome>"}`, for logs and the Stripe dashboard; Stripe treats any 200 as delivered. Payment succeeded: `confirmed`, `already_succeeded`, `late_payment_refund` (paid after the order closed; refunded), `refund_required`, `reconciliation`, `mismatch`, `contract_error`. Payment failed: `payment_failed`, `already_settled`. Refund: `refund_finalised`, `refund_already_final`, `no_matching_refund`. Any type: `unknown` (no order for this PaymentIntent), `duplicate` (event already processed), `ignored` (an event type checkout doesn't handle) |
| 400 Bad Request | `{"error": {"code": "BAD_SIGNATURE", "message": "Webhook signature did not verify."}}`: wrong or missing signature, or `STRIPE_WEBHOOK_SECRET` doesn't match the endpoint |
| 500 Internal Server Error | `INTERNAL_ERROR`: processing failed; Stripe retries the event later |
| 503 Service Unavailable | `STRIPE_UNAVAILABLE`: the body could not be parsed as a Stripe event |

Every event is processed at most once (by Stripe event ID), so Stripe's retries and replays are safe.

## Payment flow (frontend)

1. The buyer has an active hold from Reservation Service (`hold_id`).
2. `POST /api/v1/orders` with `hold_id` and `delivery_email` and an `Idempotency-Key` → `201` with `client_secret`.
3. Mount Stripe's Payment Element with the publishable key (`pk_test_…`) and `client_secret`; call `stripe.confirmPayment(...)`. Card details go straight to Stripe, never to checkout.
4. Poll `GET /api/v1/orders/{order_id}` until `status` is `CONFIRMED` (show tickets) or `EXPIRED` / `CANCELLED` / `RECONCILIATION` (show the outcome). A declined card leaves the order in `PENDING_PAYMENT` with `payment.status` `FAILED`; the buyer can try again with the same `client_secret` until the hold's deadline.

Checkout never confirms the card itself; an order moves to `CONFIRMING` only when Stripe's signed `payment_intent.succeeded` webhook arrives.

## Calls to Reservation Service

Checkout calls Reservation Service's internal API at `http://reservation-service.ticketto.local:8081` (Cloud Map; VPC only). The full contract is in [`contracts/reservation.md`](contracts/reservation.md).

| Call | When |
| --- | --- |
| `GET /internal/v1/reservations/{hold_id}` | Endpoint 1, to read and price the hold |
| `POST /internal/v1/reservations/{hold_id}/confirm` with `order_id`, `payment_reference` | After Stripe reports the payment |

## RabbitMQ messages

Checkout publishes to its own `checkout.events` exchange. Every message uses the broker envelope (`message_id`, `message_type`, `schema_version`, `occurred_at`, `producer`, `payload`), with the correlation ID in the AMQP `correlation_id` property.

| Direction | Message | Routing key / queue |
| --- | --- | --- |
| Publishes | `OrderConfirmed` | `order.confirmed` |
| Publishes | `OrderRefunded` | `order.refunded` |
| Publishes | `RefundCompleted` | `refund.completed` |
| Publishes | `RefundFailed` | `refund.failed` |
| Consumes | `EventCancelled` (event-service) | `checkout-service.EventCancelled` |
| Consumes | `ReservationExpired` (reservation-service) | `checkout-service.ReservationExpired` |
| Consumes | `RefundRequired` (reservation-service) | `checkout-service.RefundRequired` |

Payload fields are in `app/messaging/events.py` (published) and `app/messaging/payloads.py` (consumed). Unusable messages go straight to the queue's dead-letter queue; failed handling is retried up to 5 times.

## Known quirks

- A request that reaches checkout for a path or method it doesn't serve (for example `GET /api/v1/orders/{id}/extra` or `DELETE /api/v1/orders/{id}`, which the gateway's `/api/v1/orders/{proxy+}` route forwards) is answered `500 INTERNAL_ERROR` instead of `404` / `405`, because the catch-all error handler also receives Flask's own HTTP errors.
- While the database is unavailable, requests fail with `500 INTERNAL_ERROR`, not `503`.
